Mission views

Mission Views: 2-Up, 3-Up, and Quad

Mission Views keep multiple work surfaces visible for deployments, incidents, DNS changes, support triage, admin work, and documentation sprints. Use the dedicated 3-Up Top and 3-Up Bottom entries instead of guessing which tri-view will appear.

01

Getting started

Use the normal browser window for everyday browsing. Tabs, address bar, back, forward, reload, Home, Launchpad, Guide / KB, Profile, DevOps, IT Tools, Ops Panel, Mission, Settings, and About remain browser-shell controls.

Awaiting screenshotMain browser window / normal modeCapture the full browser window in normal mode with the tab strip, address bar, toolbar controls, and page area visible.

Use Home for the configured home page, Launchpad for the local start page, and the address bar for normal navigation.

02

Guide / Knowledge Base

Guide opens this local Knowledge Base. PASS128 keeps a compact Guide anchor available when the window is narrow and the full Guide button moves into More Tools.

Awaiting screenshotGuide / Knowledge Base entry pointCapture the Guide / KB entry point. At a narrow width, include the compact Guide anchor next to More Tools if possible.

Use the KB for feature walkthroughs, screenshots, keyboard hints, and operator safety notes. The KB ships as static source and does not require an online service.

03

Mission Control

Mission Control is the operational workspace for Mission Tabs, Mission Views, Runbook Rail, evidence, and local save/export workflows.

Awaiting screenshotMission Control openOpen Mission Control and capture the full window with the Mission panel, layout controls, and workbench area visible.

Open it with the Mission button, the app menu, or Ctrl+Alt+M. Small windows should still open Mission Control in compact mode instead of failing silently.

04

Mission Tabs

Mission Tabs collect related pages into a named operational workspace with roles such as console, logs, docs, runbook, ticket, monitoring, evidence, live target, vendor portal, and tool.

Awaiting screenshotMission TabsCapture a mission with tabs added and at least one role label visible.

Create or select a mission, add the active tab, assign roles, and save the mission locally. Mission state is browser-side context, not server authorization.

05

2-Up Split View

2-Up is for console plus docs, logs plus live target, or ticket plus admin console work.

Awaiting screenshot2-Up Split ViewCapture two panes with visibly different safe pages, such as docs plus a launch page.

Use the 2-Up layout when two related surfaces need to stay visible. Navigation controls target the active pane.

06

3-Up Top

3-Up Top places one wide pane above two smaller panes. It is useful for a primary console or live target over supporting docs and logs.

Awaiting screenshot3-Up TopCapture the tri-view variant with one wide pane on top and two smaller panes beneath it.

Use 3-Up Top from Mission layout controls or the command palette entry. The separate entry avoids guessing which tri-view variant the user wanted.

07

3-Up Bottom

3-Up Bottom places two smaller panes above one wide pane. It is useful for two signals feeding one larger validation or runbook surface.

Awaiting screenshot3-Up BottomCapture the tri-view variant with two smaller panes above and one wide pane on the bottom.

Use 3-Up Bottom from Mission layout controls, Ctrl+Alt+3, or the command palette entry.

08

Quad View

Quad View is the signature four-pane operator layout for deployments, DNS migrations, incidents, and IT admin work.

Awaiting screenshotQuad ViewCapture four panes in the 2x2 operator layout with the active pane clearly visible.

Use Quad when four surfaces need to stay visible. Keep the active pane obvious before using navigation or command actions.

09

Active pane routing

In Mission Views, back, forward, reload, address-bar navigation, and relevant commands target the active pane rather than a random tab.

Awaiting screenshotActive pane focus stateCapture a Mission View where the focused pane is visibly marked before navigation.

Click a pane to focus it before navigating. If a pane cannot go back or forward, the action should safely no-op without error noise.

10

Runbook Rail

The Runbook Rail stores local objective, rollback notes, checklist steps, operator notes, and mission timeline context.

Awaiting screenshotRunbook RailOpen the Runbook Rail and capture checklist, notes, or rollback fields with safe placeholder text.

Use it as the local operating checklist during a change, incident, support session, or documentation sprint. Redaction checks apply before export/sync workflows.

11

Operator Command Center

Ctrl+K opens the Operator Command Center for keyboard-first access to missions, layouts, tools, evidence, launch recipes, and handoff workflows.

Awaiting screenshotOperator Command CenterOpen Ctrl+K / Operator Command Center and capture layout, mission, and tool commands.

Use it when the toolbar is crowded or when you want fast access without moving through menus.

12

DevOps tools

The DevOps lane includes Capture, Ops Check, Deploy, Routes, Dev Audit, Ops Guard, and DevTools.

Awaiting screenshotDevOps tools laneOpen the DevOps tools lane and capture the visible tool cards.

Use these tools for deployment readiness, route/API surface review, browser diagnostics, and safe evidence capture.

13

IT tools

The IT lane includes IT Card, Endpoint, Triage, and Secret Boundary.

Awaiting screenshotIT tools laneOpen the IT tools lane and capture IT Card, Endpoint, Triage, or Secret Boundary cards.

Use these tools for helpdesk-ready support packets, endpoint/browser snapshots, service documentation, and secret-handling reminders.

14

Site View rail

Site View helps organize site/page context alongside Mission Views without losing active-pane routing.

Awaiting screenshotSite View railOpen Site View beside a safe page or Mission View and capture how site context is shown.

Use it to keep site-level context available while working in split, tri, or quad layouts.

15

Evidence and export

Evidence workflows capture URLs, titles, timestamps, notes, diagnostics, and local mission context for handoff.

Awaiting screenshotEvidence and exportCapture the evidence/export UI using safe demo content and the redaction/preview flow if available.

Preview and redact before sharing. Do not store or export cookies, auth headers, secret tokens, private keys, or PSA/API/provider secrets.

16

Downloads and installers

The downloads/installers surface should make Windows and Linux package choices clear, including checksums and known signing status.

Awaiting screenshotDownloads and installersCapture the downloads or installer surface showing package choices and checksum context.

Use checksums for package verification. Linux RPM/AppImage/DEB handoff manifests are build outputs, not source files.

17

Settings, profiles, and safety

Settings and Profiles control runtime browser preferences, privacy posture, downloads, and profile-local data behavior.

Awaiting screenshotSettings, profiles, and safetyCapture settings or profile safety controls without showing private profile data.

Profile data and runtime settings live outside source. Do not commit runtime profiles, cookies, caches, generated installers, or local data.

18

Troubleshooting states

Disabled, empty, blocked, and warning states should explain what happened and what the user can do next.

Awaiting screenshotEmpty/error/blocked stateCapture one useful troubleshooting state such as disabled integration, offline state, blocked unsafe URL, redaction warning, or empty state.

Use these screenshots to document offline state, session-expired state, blocked unsafe URL/protocol, redaction warning, or unavailable integration states.

PASS135

Add screenshots to the KB

When sanitized PNG screenshots are ready, place them in docs/kb/screenshots/ using the exact file names from the capture checklist, then run npm run kb:screenshots:ingest -- --apply. The ingestion command validates the manifest, file names, PNG signatures, size limits, and mirrors approved images into the in-app KB screenshot folder.

Missing screenshots are allowed. Missing files keep the “Awaiting screenshot” placeholders active so the KB can ship before every screen capture is available.
